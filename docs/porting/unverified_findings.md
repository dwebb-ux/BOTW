# Unverified compatibility findings

This register records evidence gaps that affect porting decisions. “Missing”
means not established by the checked-in implementation and logs, not
necessarily absent from a proprietary game binary or another runtime checkout.
Do not fill these gaps by inferring BOTW gameplay logic.

| ID | Area | Unverified finding | What is established | Evidence needed / safe next action |
|---|---|---|---|---|
| U1 | Runtime source boundary | Complete shared HLE/runtime implementations are unavailable in this repository; the patch contains only a port delta. | Patch paths and PS4 logs establish selected implementation changes and observed calls. | Inspect the exact matching shared-runtime revision when available; distinguish base code from port changes in future audits. |
| U2 | `nn::account` | No dedicated account HLE or account-to-save identity binding is established. | `acc:u0` is requested in logs; PS4 user service is initialized and used to assign controllers. | Trace guest account imports/service methods and save mount arguments; test profile isolation without changing save bytes. |
| U3 | `nn::socket` | Direct guest socket imports and Nintendo socket service behavior are not established. | PS4 DNS wrappers and optional SMB/NFS libc VFS exist. | Verify guest import table/runtime service log before adding a socket HLE or claiming network support. |
| U4 | `nn::oe` | Only two BOTW calls are registered in the narrow HLE patch; full launch/applet lifecycle is unknown. | `TryPopLaunchParameter` and `TryPopNotificationMessage` return false. | Trace observed calls and required state transitions; do not turn false-return stubs into synthetic launch data without evidence. |
| U5 | `nn::vi` | Full display mode, resize, focus, and hotplug semantics are not established. | Layer/native-window setup, host vsync event, and PS4 headless-surface/VideoOut path are documented. | Record guest VI calls and surface-change behavior on a target; replace with SDL3 surface lifecycle while preserving guest event semantics. |
| U6 | `nn::hid` | Touch, motion, and vibration behavior beyond the explicit no-sensor/no-op handlers is unknown. | Four-player Npad mapping and hotplug-style events are implemented; vibration is dropped; seven-axis returns no state. | Inventory BOTW imported HID symbols and log actual calls; test game behavior only as compatibility evidence, not as a substitute for API semantics. |
| U7 | `nn::audio` | Music/voice/SE ownership and guest mixer groups are unknown; normal audio teardown and output queue backpressure are also not established. | SDK AudioRenderer is called on a 5 ms CPU thread; PS4 output is 48 kHz stereo S16 on a separate thread. `.bwav` reads can use bounded read-ahead. | Trace renderer open/close, event cadence, queued buffer lifetime, and stream reads. Keep DSP and host sink as separate test surfaces. |
| U8 | Filesystem/resources | Guest archive reads to general runtime objects/materials/actors and resource-owner lifetime are unknown. | VFS mounts folder or pack data; offline shader tools parse a subset of shader containers. | Trace guest file imports and resource construction/destruction; do not call offline shader extraction a general resource manager. |
| U9 | Save data | Save-slot schema, load order, user binding, atomicity, and unmount/commit lifecycle are unknown. | `save:`/`cache:` map to host directories; SDK 7 `CommitSaveData` is registered to `Commit`. | Capture filesystem operations around save/load/commit and compare exact file bytes before/after; test interrupted writes on a copy. |
| U10 | Thread topology | There is no verified general asynchronous I/O thread or guest-thread-to-host-thread 1:1 mapping. | Platform/game, replay, audio, RADV, and optional render/pipeline/ASTC workers are evidenced. Filesystem reads are synchronous in the inspected PS4 path. | Collect thread names/stacks and file-read wait traces in representative workloads; avoid adding a scheduler based on assumptions. |
| U11 | Game update ordering | Order/timing among guest input processing, actors, AI, physics, and animation is unknown. | Platform input is sampled separately; NVN replay and audio rendering have dedicated runtime paths. | Instrument guest call traces only if needed for a specific compatibility defect. Do not infer the game loop from host workers. |
| U12 | Memory stack backing | Patch comments conflict: `memguard_ps4.cpp` says thread stacks use flexible memory, while `platform_ps4.cpp::start_thread` assigns guest stacks from lazy-reserved ranges and maps them through the direct-memory lazy allocator. Fallback 8 MiB pthread stack backing is not specified at the call site. | The explicit guest-stack allocation path uses lazy commit/prefault. `ps4_runtime.cpp` separately allocates the host heap from flexible-memory-first mspaces with direct-memory fallback. | Correct/clarify the stale memory-guard comment against the implementation; measure fallback-stack backing on console. Keep these pools separate in accounting. |
| U13 | Memory budgets | The PS4 direct-memory pool is shared between guest mappings and Vulkan/RADV resources; per-target peak demand and safe desktop budgets are unknown. | Patch comments document about 4.5 GiB direct memory; NVN PS4 upload buffer is 64 MiB; memory guard reports free/used values. | Profile peak guest, GPU, upload, image, and host-heap allocations separately on each target. Do not transplant PS4 capacities. |
| U14 | RomFS inventory | Staged-pack count differs between measured log evidence and old comments. | `v00.04/nx.log` reports 41,052 files/875 folders; pack script comments mention 304,207 files. | Treat count as build/run-specific; verify the exact staged dump/index used for any performance or capacity claim. |
| U15 | NVN call graph | Complete per-entrypoint BOTW call sites, signatures, and use frequency are not established. | Trace/log evidence confirms bootstrap, builders, acquire, and broad API families; the patch registers many HLE names. | Use a full matching runtime source and targeted guest trace to close only needed calls. Avoid interpreting a trace inventory as a complete call graph. |
| U16 | Vulkan backend | Exact physical-device and queue-family selection, full feature/extension requirements, and complete pipeline-cache persistence are not all established. | PS4 WSI supports graphics queue family 0 and links RADV; Vulkan work is replayed through the runtime. | Read the matching `nvn_vk.cpp` base source and test enumeration on each desktop target. Use native Vulkan WSI rather than PS4 proc shims. |
| U17 | Resource lifetime | The patch exposes object snapshots, texture incarnation adoption, alias tracking, deferred destruction, submit slots, and fence retirement, but complete base-runtime ownership rules are not available. | The relevant modifications and lifecycle boundaries are documented in [nvn_lifecycle.md](./nvn_lifecycle.md). | Preserve observed waits/retirement; validate with targeted GPU validation and stress cases before changing ownership. |
| U18 | Presentation synchronization | PS4 WSI deliberately ignores Vulkan binary semaphore waits/signals and synchronizes reuse via VideoOut flip status. The semantics of all guest-facing NVN sync combinations are not fully enumerated. | One in-order queue, flip-event wait, fence submit, and GPU-side flip/fallback are documented. | Desktop port must use standard Vulkan acquire/present synchronization; verify NVN fences/queue finish independently. |
| U19 | Shutdown | Normal guest exit, service cleanup, worker joins, save flush, and graphics/audio teardown order are not established. | `game_thread` calls `exit_process` if `nx::boot` returns; several platform workers are detached/persistent. | Capture an actual normal-exit path or define process-termination policy explicitly. Do not assume reverse startup order is safe. |
| U20 | Desktop targets | This repository does not establish a complete SDL3/Vulkan 1.3 implementation for Windows, Linux, or Steam Deck. | The PS4 implementation and shared runtime port delta are documented; a replacement mapping is proposed in [platform_replacement_plan.md](./platform_replacement_plan.md). | Build and run each target; validate driver features, guest address layout, input/audio, file paths, shaders, synchronization, and save isolation. |

## Evidence policy

1. Reuse verified findings in [architecture.md](./architecture.md),
   [graphics.md](./graphics.md), and [services.md](./services.md).
2. Inspect source only to resolve a concrete missing claim, conflict, or
   **UNVERIFIED** item; do not scan unrelated repository areas.
3. Keep runtime-implementation facts separate from logged guest behavior and
   proposed desktop replacements.
4. Do not promote a generic IPC fallback, a successful return code, or a
   single observed call into full service compatibility.
